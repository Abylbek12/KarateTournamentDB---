# План: база спортсменов клуба

Основа: `replica/sportdata/recon.md` (главный пробел: у Sportdata спортсмен заводится один раз, у нас — заново в каждой заявке).
Цель: тренер (или родитель) один раз вносит спортсмена, а на любой турнир заявляет его в два клика: «выбрать спортсмена → отметить категории».

## Что меняется для людей

1. **Новый раздел «Мои спортсмены»** в кабинете тренера и спортсмена (`#athletes`).
   Список карточек: ФИО, дата рождения, пол, пояс, последний вес, лицензия, ФИО латиницей.
   Кнопки: «Добавить», «Изменить», «В архив» (не удаляем: по нему есть прошлые заявки и результаты).
   Поиск по фамилии, если спортсменов много (в клубе их бывает 50–100).
2. **Форма заявки** начинается со списка «Мои спортсмены» с галочками:
   - отметил спортсмена → под ним сразу подходящие категории (как сейчас, по возрасту, полу, весу и поясу);
   - вес можно уточнить прямо в заявке (вес меняется от турнира к турниру), он же обновится в карточке;
   - «Новый спортсмен» открывает ту же форму, что и сейчас; после отправки он **сам попадает в базу**.
3. **Перенос старых данных.** Кнопка «Добавить из прошлых заявок» в «Моих спортсменах»: сайт собирает уникальных спортсменов
   из заявок этого аккаунта (по фамилии + имени + дате рождения) и предлагает добавить их одним нажатием.
   Ничего не переносится без нажатия.
4. Клуб пока = аккаунт тренера (как сейчас). «Несколько менеджеров у клуба» — отдельный следующий шаг (см. ниже).

Чего **не** делаем в этом шаге: фото с веб-камеры, e-mail спортсмена, базы тренеров/судей, согласие с положением.
Они в списке «потом», у каждого свои вопросы (особенно фото и e-mail детей).

## Данные

Новый раздел хранилища `athletes` (рядом с `accounts`, `events` в `server/store.ts`), **не** в общем `state`:
общий `state` рассылается всем открытым экранам, а база клуба — личная.

```ts
interface ClubAthlete {
  id: string;                 // a-<uuid>
  ownerId: string;            // аккаунт тренера/спортсмена, который ведёт карточку
  lastName: string; firstName: string;
  lastNameLatin?: string; firstNameLatin?: string;
  birthDate: string;          // ГГГГ-ММ-ДД
  gender: 'male' | 'female';
  beltRank: BeltRank; beltOther?: string;
  weightKg?: number;          // последний известный вес
  licenseNumber?: string;
  clubName?: string; city?: string; countryCode?: string;
  archived?: boolean;
  createdAt: string; updatedAt: string;
}
```

- В заявке (`participants`) появляется поле `athleteId`. Данные спортсмена **копируются** в заявку, как сейчас:
  протоколы, сетки, печать и табло работают без изменений. Правка карточки потом **не меняет** уже поданные заявки
  (как и цена, данные фиксируются при подаче).
- Хранение: `DB_KEYS` + `normalize()` + пустое значение в `emptyDb()`; на Vercel это одна строка `athletes` в `tatami_kv`,
  на ноутбуке — поле в `db.json`. Резервная копия и «Восстановить» подхватят его сами (копируется весь `db`).
- «Подготовка к запуску» (`/api/admin/launch-reset`) должна очищать и `athletes` (как удаляет аккаунты не-админов).

## Доступ (важно: многие спортсмены — дети)

- Карточки видит и меняет **только владелец** (`ownerId`) и `admin`. Никаких общих списков.
- Судьи, врач, секретарь видят данные спортсмена, как и сейчас, **через заявку** на турнир, а не через базу клуба.
- Проверка на сервере в каждом маршруте; на сайте — только показ.
- Лимит: до 500 спортсменов на аккаунт, длины полей — как в `POST /api/entries`.

## API

| запрос | что делает | кто |
| --- | --- | --- |
| `GET /api/athletes` | мои спортсмены (админ: `?ownerId=`) | вошедший |
| `POST /api/athletes` | добавить | тренер, спортсмен, админ |
| `PUT /api/athletes/:id` | изменить | владелец, админ |
| `POST /api/athletes/:id/archive` | в архив / из архива | владелец, админ |
| `GET /api/athletes/suggest-from-entries` | кандидаты из прошлых заявок этого аккаунта | вошедший |
| `POST /api/entries` (есть) | принимает `athleteId`: сервер берёт данные из карточки (только своей), иначе как сейчас и создаёт карточку | как сейчас |

Проверка повторов: та же пара «фамилия + имя + дата рождения» у одного владельца → «уже есть в базе», предложить открыть карточку.

## Что может пойти не так

- **Один ребёнок в двух аккаунтах** (родитель и тренер): это нормально, у каждого своя карточка. Повтор заявки в одну категорию
  уже ловит сервер (сравнение ФИО + даты рождения).
- **Подмена чужого `athleteId`** в запросе: сервер берёт карточку только с `ownerId` = текущий аккаунт, иначе 404.
- **Режим без интернета**: база клуба переедет на ноутбук вместе с резервной копией; заявки в зале делает секретарь, база ему не нужна.
- **Телефон**: тренеры подают заявки с телефона — список спортсменов с галочками должен быть удобен на узком экране.
- **Переводы**: все новые тексты сразу на ru / ky / en.

## Порядок работы (2–3 сессии)

1. **Сервер и хранилище**: `athletes` в store, 5 маршрутов, `athleteId` в `POST /api/entries`, автодобавление нового спортсмена,
   очистка при запуске. Тест `scripts/test-athletes.ts`: доступ только владельцу, повторы, чужой `athleteId`, лимиты.
2. **«Мои спортсмены»** (`src/components/AthletesPanel.tsx`): список, поиск, добавить / изменить / в архив, «из прошлых заявок».
   Пункт в меню тренера и спортсмена, адрес `#athletes`.
3. **Форма заявки**: сначала выбор из базы с галочками, вес в заявке, «Новый спортсмен» как сейчас; расчёт цены — тот же `pricing.ts`.
4. Проверка на тестовой копии (как с ценами), телефон, тёмная тема; ветка → превью → слияние после вашего «да».

## Потом (отдельными шагами)

- Тренеры и судьи клуба с заявкой на турнир (у Sportdata отдельные базы и регистрации).
- Несколько менеджеров у клуба: сущность `Club` с участниками-аккаунтами; карточки переходят от `ownerId` к `clubId`.
- Согласие с положением турнира перед первой заявкой (текст задаёт организатор).
- Фото спортсмена для аккредитаций и e-mail спортсмена — только после решения, как хранить данные детей.

## Вопросы к вам

1. Родитель-спортсмен тоже получает «Моих спортсменов» (например, двое детей) — или только тренер? Предлагаю: оба.
2. Номер лицензии/ID федерации — обязателен в карточке или нет? Предлагаю: необязателен.
